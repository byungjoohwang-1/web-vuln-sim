# WEB-VULN-SIM 재평가: 문제점·기능 개선·UI 고도화 구현 명세

작성일: 2026-09-13 · 대상: `C:\firebaseprojects\web-vuln-sim` · 구현 담당: GLM 코딩 에이전트

## 1. 이번 재평가의 결론

현재 플랫폼은 웹 취약점 교육을 넘어 자동차·개인정보·인프라까지 빠르게 확장되었다. 다음 고도화의 중심은 **사용자가 자신에게 맞는 실습을 찾고, 근거를 보고 해결하고, 배운 원리를 다른 상황에 적용했음을 확인하는 경험**이다.

기존 QA의 결함 목록을 그대로 다시 적용하면 이미 고친 부분을 재작업하고 새로 생긴 문제를 놓친다. 이번 문서는 실제 수정된 코드와 남은 문제를 구분했다. 가장 중요한 판단은 다음과 같다.

1. 클릭·모바일·수료증 신뢰성에 대한 개선이 이미 진행됐다. 해당 변경을 보존하고 회귀 검증한다.
2. 콘텐츠·검색·진도·AI 시나리오가 서로 다른 목록을 사용한다. 콘텐츠 추가가 학습 경험 전체로 연결되지 않는 것이 구조적 문제다.
3. AI 생성, 형식 검사, 실제 실행 검증, 교육 효과를 구분해야 한다. 각각 다른 근거가 필요하다.
4. 새 수료증 서버에는 같은 세션의 재제출과 동시 응시 제한 문제가 남아 있다. 공식 성취를 보여주기 전에 해결한다.
5. 대회에서는 **통합 사건 1개 + 맥락을 읽는 AI 코치 + 수정 전후 검증 + 새로운 문제에서의 학습 성과**를 완성한다.

대회명·심사 기준·마감·인력·예산은 미제공이다. 아래 순서는 구현 의존성과 사용자 영향에 따른 제안이며 확정 일정이나 수상 예측이 아니다. GLM은 구현 도구를 의미하며 제품 내부 모델을 GLM으로 고정하지 않는다.

이 문서에서 **확인**은 소스 또는 명시된 테스트 결과, **위험**은 코드에 근거한 발생 가능성, **가설**은 사용자 검증이 필요한 제품 판단이다. 작업 중에도 프로젝트가 갱신될 수 있으므로 GLM은 구현 직전에 관련 파일을 다시 읽는다.

## 4. 핵심 문제 재분석

### R-01. 공식 응시 세션의 재사용과 동시성 — P0

**위치:** `functions/cert.js`, `functions/test-cert.js`, `firestore.rules`.

서명·uid·만료 검사는 있지만 응시 세션을 소비한 상태가 서버에 저장되지 않는다. `handleSubmit`은 동일 sid를 다시 받아 다시 채점하고 새로운 인증서를 만든다. 메모리 DB에서 동일 정답·동일 sid를 두 번 제출해 수료증 2개 생성을 확인했다. 이것은 임의 정답 없이 합격할 수 있다는 뜻은 아니지만 중복 발급과 반복 채점 경로가 존재한다는 뜻이다.

`handleStart`의 횟수 처리는 `get → n+1 → set`이며 트랜잭션이 아니다. 메모리 DB에서 병렬 5회가 모두 통과하고 n=1이 남았다. 운영에서 같은 수치가 재현된다는 단정은 하지 않되, 코드의 동시성 보장은 없다.

추가로 서명키 최초 생성도 `get → 임의 키 생성 → set`이다. 여러 인스턴스가 최초 접근하면 다른 키를 캐시할 위험이 있다. 이 항목은 코드 기반 위험이며 별도 재현이 필요하다.

**개선:** 서버 응시 문서에 uid, 문항 버전, 시작/만료 시각, 제출 상태, 결과 ID를 저장한다. 횟수 차감과 세션 생성은 원자적으로 처리한다. 첫 최종 제출은 합격/불합격 모두 세션을 소비한다. 동일 요청 재전송에는 기존 결과를 반환하고 변경된 답안 재제출은 거부한다. 채점·결과·성취 기록도 부분 성공 후 중복되지 않게 한다. 서명키는 안정적으로 프로비저닝하고 key ID와 교체 정책을 둔다.

**완료 기준:** 동일 sid의 순차/동시 제출 모두 결과 1개, 불합격 후 답안 교체 재제출 거부, 병렬 응시도 일일 한도 준수, 타인·만료 세션 거부, 네트워크 재시도 시 결과 복구. 문항 버전은 세션 시작 시점에 고정한다.

### R-02. 콘텐츠는 늘었지만 데이터 연결이 불완전함 — P1

**확인:** 검색 513개와 진도 463개는 목적이 다르므로 차이 자체는 결함이 아니다. 실제 결함은 다음 연결 누락이다.

- `vulnlab.html`, `redteam.html`, `quiz-forge.html`은 완료 이벤트를 보내지만 `progress-catalog.json`에 없다. `my-progress.html`의 완료 수·분야별 집계는 카탈로그를 순회하므로 XP와 표시 완료 목록이 어긋날 수 있다.
- `15_privacy-*`는 진도 카탈로그에 포함되지만 `progress.js`의 `LEARNABLE` 정규식에는 없다. 해당 페이지에서 자동 방문 기록/칩 노출 경로가 제외된다.
- 도구 전체를 한 페이지 ID로 완료 처리한다. 다른 미션을 수행해도 동일 완료 상태로 묶여 세부 역량을 설명하기 어렵다.
- 개인정보 페이지는 존재하지만 `scenarios.json`에는 개인정보 도메인이 없다. 해당 데이터를 읽는 레드팀/문제 포지에는 확장 내용이 자동 연결되지 않는다.

**원인:** 파일명 규칙·생성기·UI 목록·진도 API에 콘텐츠 정의가 분산되어 있다.

**개선:** 공통 카탈로그에서 검색·진도·AI 후보 목록을 목적별로 생성한다. 단기에는 누락을 수정하고 장기에는 `pageId`와 `activityId`를 분리한다. 기존 완료 기록은 보존하되 새 상세 미션을 완료한 것으로 변환하지 않는다.

**완료 기준:** 대표 도구/개인정보 실습 완료가 내 기록에 나타남, 집계와 XP 설명 일치, 새 분야 추가 후 수동 정규식 수정 불필요, 검색 제외/진도 제외 사유 명시.

### R-03. 검색 데이터와 검색 UI의 결함 — P1

**위치:** `public/js/soc-chrome.js`, `public/data/search-index.json`, `_gen/gen_search_index.py`.

- 카탈로그 HTML에는 자동차 한글 키워드가 보강됐지만 전역 검색 인덱스의 `t/k/u`에서 `자동차` 일치는 0개다. 예를 들어 AUTO-01의 k는 `14 auto auto01`이다. 허브 검색과 전역 검색 품질이 달라질 수 있다.
- 인덱스 로딩 후 `runSearch('')`를 호출하므로 먼저 입력한 검색어와 표시 결과가 어긋날 수 있다.
- 빈 검색의 `render(t('quick'))`는 `render`의 메시지 분기로 들어가 결과 행 대신 안내만 그린다. 추천 결과는 내부에 있지만 처음 열었을 때 보이지 않는 코드 경로다.
- 검색 실패 후 `INDEX_TRIED`가 유지되어 같은 페이지에서 복구 재시도가 어렵다.
- dialog의 모달 의미, 포커스 가두기·복귀, 결과 링크 의미가 부족하다.

**개선:** 제목/분야/동의어/CWE/역량/시간/실습 유형을 인덱싱한다. 로딩 완료 시 현재 입력값으로 검색한다. 상태를 loading/ready/error로 분리하고 재시도를 제공한다. 추천 제목과 결과 목록 렌더링을 분리한다. 결과는 실제 링크를 기본으로 만든다.

**완료 기준:** `자동차`, `차량 인증`, `개인정보`, `인가`, `CAN` 검색의 기대 결과 세트 통과. 느린 로딩 중 입력 보존, 오프라인 후 재시도, Tab/Enter/Escape 및 포커스 복귀 성공. 의미 검색은 이 기본 품질을 확보한 다음 평가한다.

### R-04. AI 문제 검증의 의미가 불명확함 — P1

`quiz-forge.html`의 V2는 선택지 문자열 중복과 정답 인덱스를 검사하고, V3는 해설 길이를 검사한다. 이 검사는 의미상 정답의 유일성이나 설명의 정확성을 보장하지 않는다. 위험 패턴 정규식도 코드의 실제 취약 여부를 증명하지 않는다.

규칙 생성 실패 시 배지는 수정됐지만 실패 문제를 참고용으로 출제한다. 또 규칙 생성 통과는 AI 통과와 같은 방식으로 `pass` 통계에 반영되지 않아 지표 해석이 모호하다.

**개선:** 생성 방식과 검사 종류를 별도 필드로 저장한다. UI에는 `형식 검사 통과`, `실행 테스트 통과`, `내용 검토 완료`를 실제 근거가 있을 때만 표시한다. 실패 문제는 기본 학습 흐름에서 제외하고 제작자 검토함에 둔다. AI 재검토만 수행했다면 `AI 검토`라고 표시한다.

**완료 기준:** 실패 문항은 추천·시험·검증 성취에 포함되지 않음. 정답 모호/잘못된 해설/형식 오류를 넣은 고정 평가 세트로 오탐·누락 기록. 생성 요청 수, 후보 수, 각 검사 통과 수, 최종 출제 수를 구분.

### R-05. 성취 표시가 실제로 평가한 범위보다 넓어질 위험 — P1

서버 채점과 서명은 발급 기록의 신뢰도를 높이지만, 현재 16문항 객관식 평가만으로 모든 도메인의 실무 역량을 증명할 수는 없다. 마찬가지로 ‘안전한 상태’ 버튼을 선택해 결과 애니메이션을 본 것은 직접 취약점을 수정한 것과 다르다.

**개선:** `학습 활동`, `지식 평가 통과`, `실습 검증 통과`, `새 상황 적용`을 나눠 표시한다. 수료증에는 평가 버전·영역·유형·통과 기준을 적는다. 개념 시뮬레이션은 유지하고 대표 실습에서 학습자가 설정/코드를 직접 선택·수정하도록 확장한다.

**완료 기준:** 각 배지에서 무엇을 측정했는지 설명 가능. 상태 전환 애니메이션을 실장비 침투시험이나 보안 적합성 평가로 표현하지 않음. 코드/설정 수정 실습은 정상 동작 유지와 비인가 동작 차단을 함께 검사.

### R-06. 시작점과 메뉴가 학습 목표보다 도구 중심임 — P1 제품 가설

루트 홈은 4트랙 입구이고 공통 로고는 SOC 허브로 이동한다. 레드팀·실습장·문제 포지 등 도구명만 보고 초보자가 첫 행동을 고르기는 어려울 수 있다. 개선 여부는 사용자 과제로 확인한다.

**개선:** 홈을 하나의 공식 시작점으로 정하고 `바로 체험`, `내 수준 진단`, `이어서 학습`을 제시한다. 분야별 탐색과 전문가용 도구 접근은 유지한다. 도구명 옆에는 ‘공격을 분석하고 방어 연습’, ‘취약점을 직접 수정’처럼 결과를 설명한다.

**완료 기준:** 신규 사용자가 도움 없이 첫 적합한 실습을 시작할 수 있음. 내비게이션에서 현재 위치와 홈 동작 일관. 기존 깊은 링크는 유지. 사용자 5명 이상에게 첫 실습 진입 시간과 혼동 지점 관찰.

### R-07. 모바일·공통 UI는 패치 이후의 통합 설계가 필요함 — P1

본문 밀림과 메뉴 줄바꿈은 수정됐다. 그러나 헤더가 여러 구현으로 나뉘고 고정 언어바 CSS도 남아 있다. 기존 겹침이 최신 화면에서도 동일하다고 단정하지 않고 대표 화면을 다시 확인해야 한다. 언어바를 희미하게 만드는 처리만으로 충돌이 없어졌다고 보기도 어렵다.

**개선:** 공통 헤더·검색·언어·알림의 배치 규칙을 만든다. 넓은 화면에서 정보 밀도를 유지하되 모바일은 목표/증거/실습/코치를 탭으로 나눈다. 분야색보다 상태·현재 단계·핵심 행동을 먼저 보이게 한다.

**완료 기준:** 320/390/768/1440px에서 본문·CTA·언어·상태 겹침 없음, 확대 200%에서 사용 가능, 키보드 포커스가 고정 UI에 가려지지 않음. 코드/표 내부 스크롤과 페이지 전체 넘침을 구분하여 검사.

### R-08. 분야 확장에 비해 콘텐츠 검토 체계가 약함 — P1

개인정보 판단기·처리방침 작성기와 자동차 센서/프로토콜 콘텐츠는 이미 있다. 다음 필요한 것은 동일 도구를 더 만드는 작업보다 출처·적용 조건·검토 이력·시뮬레이션 한계를 관리하는 기능이다. 이번 조사로 개별 법적 결론의 정확성을 판정한 것은 아니다.

**개선:** 콘텐츠에 출처 ID, 문서 버전, 적용 국가/환경, 검토일, 검토 상태를 둔다. 개인정보 판단 결과에는 입력 가정·판정 근거·추가 확인 사항을 함께 출력한다. 처리방침 생성물은 사용자의 실제 처리 현황과 대조할 수 있어야 한다. 자동차/OT는 모델에서 검증한 조건과 실제 장비 검증을 구분한다.

**완료 기준:** 대표 사건 모든 단계에서 근거를 열 수 있음. 검토되지 않은 법령 변경을 ‘최신 반영 완료’로 표시하지 않음. 검토일이 없으면 ‘미검토’ 표시. 출처 URL 존재 검사와 내용 전문가 검토는 별도 관리.

### R-09. AI 호출 운영과 데이터 최소화 — P1/P2

전체 호출 한도는 추가됐다. 그러나 Firestore 오류 시 프로세스 메모리로 폴백하므로 다중 인스턴스·재시작 환경에서 전역 한도가 그대로 보장되지는 않는다. 기존 BYO API 키의 localStorage 저장 경로도 남아 있다.

**개선:** 유료 호출은 공통 예산 저장소 실패 시 정적 코칭으로 전환하는 정책을 권장한다. 공급자별 토큰/비용 예약·정산, 중복 요청 제어를 둔다. 로그인 토큰 검증과 앱 무결성 검증은 역할을 구분하고 기존 익명 체험은 정적 모드로 유지한다. App Check는 남용 위험을 줄이는 보조 통제이며 권한 검증의 대체물이 아니다. [Firebase App Check](https://firebase.google.com/docs/app-check)

코치에는 실습 ID·선택한 증거·실패 조건·필요한 최소 발췌만 전달한다. 사용자가 붙여 넣은 로그의 토큰·개인정보를 마스킹하고 전송 미리보기를 제공한다. 브라우저 개인 키 영구 저장을 기본 흐름에서 제거한다. 세션 저장으로 바꾸더라도 활성 페이지의 스크립트가 읽을 수 있다는 한계는 남는다.

**완료 기준:** 429/타임아웃/예산 저장소 장애에도 진행 기록 보존, 호출 방식 정확히 표시, 재시도 폭주 없음, 개인 키·토큰이 진도 동기화 및 분석 로그에 포함되지 않음.

| 1 | 통합 활동 기록 | progress, my-progress, 각 도구 | 과제 ID·활동/검증 구분·누락 어댑터 | 한 화면에서 실제로 한 학습을 확인 |

| 4 | 통합 사건 1개 | breach-campaign, vulnlab, 자동차/개인정보 실습 | 같은 사건 ID와 단계 간 증거 전달 | 도메인을 연결해 문제 해결 |

## 6. UI 고도화 명세

### 6.1 정보 구조

- 전역 메뉴: **홈 / 분야별 학습 / 사건 실습 / 내 성장**. 검색·언어·계정은 공통 헤더.
- 분야: IT·웹/API, 인프라·클라우드, 산업·OT, 자동차, 개인정보, AI, 금융, 기타 경로.
- 교차 필터: 직무, 수준, 예상 시간, 학습 목표, 실습 유형. 같은 콘텐츠를 여러 분야에서 연결하되 복제하지 않는다.
- 전문가 도구는 ‘실습 도구’에서 바로 열 수 있게 유지한다. 대회 데모를 위해 기존 기능을 숨기는 식으로 재구성하지 않는다.

### 6.2 홈

```text
[로고] [분야별 학습] [사건 실습] [내 성장]      [검색] [언어] [계정]

보안 사고를 직접 해결하며 배우세요.
[대표 사건 체험] [내 수준 진단]  ← 진단은 선택

[이어서 학습: 지난 단계 / 저장 상태 / 계속]
[추천 3개: 배울 역량 · 시간 · 추천 이유 · 시작]

[분야 탐색: IT / 산업·OT / 자동차 / 개인정보 / AI / 더 보기]
[최근 학습 결과: 실제 저장된 활동과 검증 결과]
```

신규 사용자에게는 ‘이어서 학습’ 대신 입문 과제를 표시한다. 잘못된 인기 수치·가상 완료율·예시 XP를 실제 데이터처럼 표시하지 않는다. 보유 콘텐츠 수는 정의와 함께 자동 집계한다.

### 6.3 실습 화면

```text
학습 경로 > 자동차 > 업데이트 검증              [저장됨]
목표 확인 → 증거 분석 → 수정 → 재검증 → 설명

┌ 목표 / 증거 목록 ┬ 실습·로그·코드 / 변경 전후 ┬ AI 코치 ┐
│ 성공 조건       │ [검증 실행] [초기화]       │ 힌트 단계│
│ 선수 지식       │ 정상/비인가 테스트 결과    │ 근거 링크│
└─────────────────┴───────────────────────────┴──────────┘
```

- 1200px 이상: 좌측 약 220px, 가운데 유동, 코치 약 320px. 콘텐츠 최소 폭을 보고 조정한다.
- 768~1199px: 코치를 접고 필요 시 패널로 연다.
- 768px 미만: 목표 요약 + `실습 / 증거 / 코치` 탭. 탭 이동 시 입력·스크롤·실행 결과 유지.
- 실행 버튼과 제출 버튼의 의미를 분리한다. 초기화는 지워지는 항목을 설명하고 취소 가능하게 한다.
- 오류는 ‘검증 실패: 타인의 정보 조회가 아직 허용됩니다’처럼 실패 조건과 다음 확인 지점을 표시한다.

### 6.4 내 성장

첫 화면에는 이어서 학습, 최근 결과, 추천 복습을 먼저 배치한다. XP·레이더는 보조 정보로 둔다. 평가 결과에는 `지식 평가`, `실습 테스트`, `새 상황 적용`을 구분하고 해당 증거로 이동하게 한다. 레이더는 근거가 부족한 분야를 0점으로 단정하지 말고 ‘미측정’으로 표시한다.

### 6.5 공통 시각 규칙

| 요소 | 제안 |
|---|---|
| 타이포그래피 | 한글 본문 16px/1.6 기준, 제목 28~32px, 코드만 모노스페이스 |
| 색 | 배경 `#0B1220`, 표면 `#152033`, 본문 `#F1F5F9`, 보조 `#B6C2D4`, 강조 `#38BDF8`를 후보 토큰으로 사용. 실제 조합 대비 검사 필수 |
| 의미 | 선택·진행·성공·경고·실패 색의 용도를 고정하고 아이콘/문구 병기 |
| 간격 | 4/8px 단위, 카드 내부 16~24px, 페이지마다 별도 여백 체계 생성 금지 |
| 버튼 | 주요 행동 1개를 강조, 주요 터치 제어 높이 44px 권장 |
| 장식 | 긴 애니메이션·과도한 발광 대신 증거 변화와 검증 결과를 강조 |
| 공통 셸 | 헤더·언어·검색·상태·포커스·레이어 순서를 공통 CSS/모듈로 관리 |

터치 대상의 WCAG 2.2 AA 최소 기준은 원칙적으로 24×24 CSS px이며 간격 등 예외가 있다. 44px는 여기서 제안하는 주요 제어의 사용성 목표다. 작은 요소를 모두 규정 위반으로 집계하지 않는다. [W3C 대상 크기 기준](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

### 6.6 필수 상태 설계

| 상태 | UI 동작 |
|---|---|
| 로딩 | 진행 문구와 취소 가능한 작업 안내, 중복 실행 방지 |
| 빈 결과 | 필터 초기화·유사 분야·입문 추천 제공 |
| AI 이용 불가 | 정적 힌트 전환을 표시하고 현재 실습 유지 |
| 저장 실패 | ‘저장됨’을 표시하지 않으며 재시도·로컬 내보내기 제공 |
| 오프라인 | 가능한 학습 범위 표시. 서버 시험/발급은 연결 필요 안내 |
| 업데이트 | 저장 후 새로고침 선택. 시험 중 강제 새로고침 금지 |
| 영어 미지원 | 한국어 유지와 지원 범위 명시. 본문이 한국어인 채 문서 언어만 en으로 바꾸지 않음 |

## 7. 대표 사건과 AI 차별화

### 7.1 제출용 최소 사건

가상의 모빌리티 기업에서 발생한 차량 데이터 접근 사건을 사용한다. 기술적으로 한 취약점이 자동으로 다른 시스템 침해로 이어진다고 묘사하지 않는다. 단계 사이에 제공되는 권한·로그·데이터와 가정을 명시한다.

1. **API 권한 문제:** 사용자 A/B 요청을 비교하고 소유권 검사를 수정한다.
2. **차량 업데이트 검증:** 서명·버전·대상 정책을 설정하고 정상/변조 패키지를 구분한다.
3. **개인정보 대응:** 합성 데이터에서 영향 범위·접근권한·대응 기록을 정리한다. 기존 대응 훈련을 연결한다.
4. **보고와 전이:** 증거 기반 보고서를 작성하고, 같은 인가 원리를 다른 자산 문제에 적용한다.

OT·산업기술 단계는 이 최소 흐름을 완주한 뒤 확장한다. 3~5분 발표에서는 준비된 중간 상태로 이동할 수 있어야 하며 데모 데이터임을 표시한다.

### 7.2 AI 코치 계약

- 입력: activityId, 콘텐츠 버전, 현재 단계, 관찰한 증거 ID, 실패한 테스트 ID, 사용한 힌트 수.
- 출력: 관찰 요약, 다음 확인 행동, 힌트 단계, 유효한 출처 ID, 불확실성/보류 사유.
- 서버는 출처 ID가 허용된 콘텐츠인지 확인한다. 존재 확인만으로 인용 내용의 정확성이 검증된 것은 아니다.
- 실습 문서/로그 속 지시는 신뢰하지 않는다. AI는 답안 제출·점수 기록·도구 권한 변경을 수행하지 않는다.
- 최종 채점은 고정된 검사기에서 수행한다. AI 설명 품질과 채점 결과를 별도로 기록한다.
- 새 정답 공개는 학습자의 명시적인 ‘해설 보기’ 행동으로 제한하고 기록한다.

### 7.3 교육 효과 확인

AI 없는 정적 힌트와 AI 코치를 같은 난이도의 과제에서 비교한다. 동일 문제 반복 효과를 줄이도록 사전/사후 변형 문항을 사용한다. 사용자를 소수만 관찰했다면 탐색적 결과로 표시한다.

측정: 최초 실습 진입 시간, 첫 실패 후 다음 유효 행동까지 시간, 미션 완주율, 정답 공개 전 해결률, 전이 문항 정답률, 잘못된 AI 안내 비율, 성공한 학습 세션당 AI 비용. 발표에서는 측정 대상 수·평가 방식·실패 사례도 함께 보여준다.

## 8. 데이터·구현 구조

### 8.1 공통 카탈로그 제안

`public/data/content-catalog.json`을 새로 도입하되 기존 검색/진도 JSON은 호환 출력으로 유지한다.

```json
{
  "id": "auto.ota.integrity",
  "page": "14_auto-auto04.html",
  "domains": ["automotive"],
  "skills": ["integrity", "authorization"],
  "keywords": ["자동차", "차량", "업데이트", "OTA"],
  "level": "intermediate",
  "estimatedMinutes": null,
  "learningMode": "concept_simulation",
  "progressEnabled": true,
  "aiEligible": false,
  "validationKinds": [],
  "contentVersion": "1",
  "reviewStatus": "unreviewed",
  "sourceIds": []
}
```

위 ID와 페이지 연결은 구조 예시이며 실제 내용 대조 후 확정한다. 시간·검토·검증 상태를 생성기가 임의로 채우지 않는다. 콘텐츠 분류와 실습 실행 방식은 서로 다른 필드로 둔다.

### 8.2 활동과 검증 기록

- 활동: eventId, pageId, activityId, attemptId, contentVersion, visited/attempted/completed, 사용한 힌트.
- 검증 결과: serverResultId, 검증기 버전, 테스트별 결과, evidenceIds, 서버 시각.
- 클라이언트가 보낸 `verified: true`를 신뢰하지 않는다. 공식 결과는 서버 원본과 결합한다.
- 재전송 eventId는 중복 집계하지 않는다. 오프라인 기록은 활동으로 병합하고 서버 검증 성취로 승격하지 않는다.
- 기존 localStorage를 일괄 삭제하지 않는다. 버전 어댑터와 내보내기/복구를 먼저 제공한다.
- 학습 이벤트는 필요한 최소 필드만 수집한다. 강사에게 원문 AI 대화 전체를 기본 공유하지 않는다.

Firestore 클라이언트 규칙에는 허용 필드·형식·변경 가능한 필드를 명시한다. 서버 Admin SDK 경로의 검증은 규칙과 별도로 구현해야 한다. [Firestore 필드 접근 제어](https://firebase.google.com/docs/firestore/security/rules-fields)

### 8.3 파일별 작업 지도

| 작업 | 기존 수정 대상 | 새 파일 제안 |
|---|---|---|
| 응시·발급 원자성 | functions/cert.js, functions/test-cert.js, firestore.rules | 필요 시 서버 session 모듈 |
| 통합 카탈로그 | _gen/gen_progress_catalog.py, _gen/gen_search_index.py, _gen/gen_scenario_tools.py | content-catalog 스키마·검사기 |
| 진도 호환 | public/js/progress.js, public/my-progress.html, 세 실습 도구 | activity-adapter.js |
| 검색·공통 UI | public/js/soc-chrome.js, public/js/bilingual.js, 각 대표 헤더 | public/css/platform-tokens.css |
| 홈·경로 | public/index.html, public/vuln-hub.html, skill-assess/mission-board | 필요할 때만 경로 데이터 JSON |
| 문제 검증 | public/quiz-forge.html, question-admin.html, 관련 생성기 | 고정 평가 fixture |
| 대표 사건 | breach-campaign.html, 기존 자동차/개인정보/웹 과제 | 사건 정의 JSON과 증거 fixture |
| 회귀 검사 | tools/validate-public-site.js, tools/test-firestore-rules.js | 대표 여정 브라우저 테스트 |

프레임워크 전면 교체는 선행 조건이 아니다. 기존 정적 HTML/Firebase 구조에서 대표 화면 공통화부터 진행한다. 생성 파일은 해당 생성기도 함께 수정하되 수백 개 파일의 무차별 재생성을 피한다.

## 9. GLM 작업 패키지와 완료 기준

P0는 공식 기능의 신뢰성 차단, P1은 핵심 여정 품질, P2는 검증 후 확장이다.

| ID | 우선순위 | 구현 범위 | 선행 작업 | 완료 증거 |
|---|---|---|---|---|
| G01 | P0 | 응시 세션 1회 소비·동시 횟수 제한·안정적 서명키 | 없음 | 재제출/동시성/만료/복구 테스트 |
| G02 | P1 | 도구 카탈로그·개인정보 진도 누락 수정 | 없음 | 도구/개인정보 각 1개 완료 후 집계 일치 |
| G03 | P1 | 검색 동의어·추천 목록·로딩 경쟁·재시도·포커스 | 없음 | 기대 검색어 세트와 키보드 테스트 |
| G04 | P1 | AI 검증 용어·실패 출제 정책·통계 분리 | 없음 | 실패 fixture가 평가에 진입하지 않음 |
| G05 | P1 | 공통 헤더·언어·모바일 레이아웃·홈 입구 | G03 | 대표 화면 4개 폭, 확대, 키보드 확인 |
| G06 | P1 | 공통 카탈로그와 버전 어댑터 | G02 | 기존 기록 유지·재생성 차이 검토 |
| G07 | P1 | 맥락 코치와 증거 전달 | G04, G06 | 정답/권한 조작 요청 거부·출처 검증 |
| G08 | P1 | 대표 사건과 검증 리포트 | G01, G06, G07 | 시작→수정→검증→내 성장 완주 |
| G09 | P2 | 오개념 복습·강사 리포트·새 산업 경로 | G08 | 사용자 관찰로 효과/혼동 확인 |

기간을 먼저 약속하지 말고 G01~G04 완료 후 팀 처리량으로 일정을 다시 산정한다. 짧은 마감이라면 G09를 뒤로 미루고 대표 사건의 단계 수도 줄인다.

### 9.1 필수 검증

- 정적 검사: 현재 검사 통과 + 필요한 배포 파이프라인에서 `node tools/validate-public-site.js --online` 원격 SRI 대조.
- 서버: `node functions/test-cert.js`에 세션 재사용/동시성/실패 후 재제출/버전 고정 테스트 확장. 기존 테스트 통과만으로 새 문제 해결 판정 금지.
- 규칙: `firebase emulators:exec --only firestore "node tools/test-firestore-rules.js"`. 허용된 본인 활동과 거부되어야 할 공식 결과 쓰기를 함께 확인.
- 브라우저 대표 여정: 홈→검색→실습→실패 힌트→수정→검증→내 성장. 자동차/개인정보/핵심 도구 각각 포함.
- 반응형: 320/390/768/1440px, 키보드/200% 확대, 폼 레이블/명암 대비/모달 포커스. 접근성 자동 검사와 수동 탐색 병행.
- AI: 타임아웃·429·잘못된 JSON·허위 출처·문서 속 악성 지시·정적 폴백. 재시도 중 중복 과금/중복 기록 확인.
- 배포: 서비스 워커 갱신·이전 캐시·새 버전 안내·기존 기록 호환. 운영에서 읽기 중심 스모크 검사 후 버전 기록.

### 9.2 GLM에 전달할 실행 프롬프트

```text
프로젝트: C:\firebaseprojects\web-vuln-sim
기준 문서: docs/SECURITY_PLATFORM_REASSESSMENT_GLM_2026-09-13.md

1. 현재 코드와 작업 지침을 먼저 읽고, 이 문서 작성 후 수정된 부분을 확인하라.
2. 사용자 미커밋 변경과 기존 URL/학습 기록을 보존하라.
3. 이미 수정된 SRI·모바일·script·서버 발급 기능을 다시 만들지 말라.
4. G01부터 패키지별로 구현하고 원인·변경 파일·검증 결과를 기록하라.
5. 작업 패키지의 완료 기준을 충족하기 전 다음 확장 패키지로 넘어가지 말라.
6. 생성물은 생성기와 함께 검토하되 전체 재생성 결과를 무조건 덮어쓰지 말라.
7. 실제 테스트 없는 '검증됨', 근거 없는 '최신/전수/안전', 가짜 성과 수치를 만들지 말라.
8. 필요한 스키마 이행·실패 복구·오프라인·키보드/모바일 상태를 함께 구현하라.
9. 본 문서는 구현 요청의 기준이며 자동 운영 배포 지시가 아니다. 세션에서 별도로
   부여된 배포 권한이 있다면 그 범위와 프로젝트 지침에 따라 처리하라.
10. 패키지별 결과에 완료/미완료/검증하지 못한 항목을 구분하고 남은 위험을 적어라.
```
