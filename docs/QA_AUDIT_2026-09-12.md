# WEB-VULN-SIM QA 분석 및 고도화 제안

점검일: 2026-09-12  
대상: 로컬 `C:\firebaseprojects\web-vuln-sim\public` 및 운영 `https://vuln-sim.web.app/`

## 1. 결론

콘텐츠 양, 실제 브라우저형 취약점 실습, AI 레드팀, 문제 생성·검증 콘셉트는 대회 데모로 강하다. 현재 가장 큰 위험은 콘텐츠 부족이 아니라 **회귀 결함, 모바일 붕괴, 검증되지 않은 점수·수료증, 제품 입구의 분산**이다.

대회 제출 전에 아래 5개를 반드시 해결해야 한다.

1. 운영 카탈로그 접기/펼치기 복구
2. `vuln-hub.html` 및 `training-dashboard.html` 모바일 레이아웃 복구
3. 레드팀/문제 포지 공통 스크립트 태그 복구
4. 운영 수료증의 개발자 우회 기능 제거 및 서버 검증 발급
5. 루트 홈과 대회용 허브를 하나의 제품 입구로 통합

새 콘텐츠를 더 추가하는 작업은 이 항목들보다 뒤에 둔다.

## 2. 점검 범위와 방법

- 정적 검사: 최상위 HTML 428개, JavaScript 25개
- 운영 링크 검사: 검색 인덱스의 426개 페이지 전부 HTTP 200 및 `text/html` 확인
- 브라우저 기능 검사: Chromium으로 홈, 허브, 취약점 실습장, 레드팀 아레나, AI 문제 포지, 진도, AI 튜터, 훈련 대시보드, 자동차/ICS/AI 대표 실습, SQL 라이브 실습 확인
- 화면 크기: 1440×900, 768px, 390×844
- 접근성 자동 검사: axe-core 4.10.2, WCAG A/AA 규칙 표본 검사
- 기능 스모크: 카탈로그 열기/닫기, 검색, 취약점 패치 토글, 문제 생성 폴백, 레드팀 1라운드 진행
- 운영 성능 관찰: 일반 네트워크에서 초기 요청 수와 전송량 확인. 모바일 저속망 Lighthouse 점수는 이번 점검 범위에 포함하지 않음

정적 링크 검사는 통과했지만 실제 동작 결함이 여러 개 발견됐다. 현재 검증 도구가 DOM 클릭, 외부 스크립트 무결성, 모바일 레이아웃을 검사하지 않기 때문이다.

## 3. 잘된 점

- 검색 인덱스의 운영 페이지 426개가 모두 정상 응답한다.
- `scenarios.json`의 도메인별 합계와 메타 총계가 230개로 일치한다.
- 취약점 실습장은 가상 서버, Repeater, 코드/패치, AI 코치를 한 화면에 묶어 교육 흐름이 명확하다.
- 레드팀 아레나는 로컬 규칙 엔진 폴백에서도 약 1.4초 안에 선택지 3개를 만들고 1라운드를 완료했다.
- 운영 AI 프록시의 상태 확인은 정상이며, 공급자 장애 시 규칙 엔진으로 이어지는 설계가 있다.
- 주요 화면의 초기 전송량은 과도하지 않았다. 관찰값은 홈 약 16KB, 허브 약 205KB, 레드팀 약 92KB, 문제 포지 약 89KB였다. 이는 네트워크 환경에 따른 1회 관찰값이지 성능 등급은 아니다.
- `vulnlab.html`의 iframe은 `sandbox="allow-scripts"`로 분리되어 같은 출처 권한을 함께 주지 않는다.

## 4. 발견된 결함

### P0 — 배포 및 대회 시연을 막는 문제

#### QA-P0-01 운영 카탈로그가 클릭되지 않음

- 위치: `public/vuln-hub.html`
- 운영 재현: 기반시설 가이드 아래 UNIX/Windows/DBMS/보안장비 등을 클릭해도 내용이 열리지 않는다.
- 원인: Bootstrap bundle의 `integrity` SHA-384 문자열에 `/` 한 글자가 빠져 브라우저가 스크립트를 차단한다.
- 증거: 운영 Chromium에서 `bootstrap === undefined`, SRI digest 오류가 발생했다.
- 상태: 로컬 파일과 `_gen/rebuild_hub_soc.py`에는 수정되어 있으나 운영 배포본에는 아직 반영되지 않았다.
- 완료 기준: 운영 브라우저에서 8개 하위 카테고리가 마우스와 키보드로 열리고 닫히며 콘솔에 SRI 오류가 없어야 한다.

#### QA-P0-02 대회 허브 모바일 화면이 왼쪽으로 밀림

- 위치: `public/vuln-hub.html`
- 운영 재현: 390px 화면에서 본문이 왼쪽으로 약 320px 이동해 제목, CTA, 카드, 카탈로그가 잘린다.
- 측정: `.soc-main`의 좌표가 `left=-320`, `right=605`, 폭 925px였다. 문서는 `overflow-x:hidden`이라 사용자가 숨은 영역으로 이동할 수도 없다.
- 원인: 이전 모바일 사이드바 규칙의 `position`, `transform`, `max-width`, `min-height`가 새 SOC 테마에서 완전히 초기화되지 않았다.
- 완료 기준: 320/360/390/768px에서 모든 주요 요소가 뷰포트 안에 있고, 숨겨진 가로 콘텐츠가 없어야 한다.

#### QA-P0-03 레드팀/문제 포지 공통 내비게이션 로드 실패

- 위치: `public/redteam.html`, `public/quiz-forge.html`
- 현재 태그: `src="/js/soc-chrome.js data-topbar="off""`
- 실제 요청: `/js/soc-chrome.js%20data-topbar=` → 404
- 영향: 두 핵심 대회 화면에서 통합 탑바와 Ctrl+K 검색이 로드되지 않는다.
- 완료 기준: 태그를 올바른 `src`와 `data-topbar="off"` 속성으로 분리하고, 콘솔 오류 0건 및 Ctrl+K 검색 성공을 확인한다.

#### QA-P0-04 훈련 대시보드 모바일 가로 폭 1,032px

- 위치: `public/training-dashboard.html`
- 운영 측정: 390px 뷰포트에서 문서 폭이 1,032px다.
- 원인: 기존 헤더의 `.nav-links`가 905px 너비로 한 줄에 유지된다. 공통 탑바와 페이지 전용 내비게이션도 중복된다.
- 영향: 주요 학습 메뉴가 화면 밖에 놓이고 모바일에서 페이지 전체가 좌우로 움직인다.
- 완료 기준: 페이지 전용 긴 메뉴를 `더보기`/드로어로 바꾸고 문서 폭이 뷰포트와 같아야 한다.

#### QA-P0-05 운영 수료증 우회 및 검증 신뢰성 문제

- 위치: `public/certificate.html`, `public/auth-widget.js`, `firestore.rules`, `public/verify.html`
- 운영 화면에 `🧪 [개발자 테스트] 진도 강제 달성 처리` 버튼이 그대로 노출된다.
- 운영에서 `typeof window.forceUnlockForDev === "function"`임을 확인했다.
- 이 함수는 개념·실습 완료와 XP를 브라우저에서 만들어 수료 조건을 즉시 충족한다.
- 수료증 해시는 공개 데이터의 단순 SHA-256이라 서명이 아니다. 사용자가 같은 방식으로 임의 자격 데이터를 만들 수 있다.
- Firestore는 `certificates` 생성 시 `uid`만 본인인지 검사한다. 점수, 과정, 날짜, 해시가 실제 서버 채점 결과인지 확인하지 않는다.
- `leaderboard/{uid}`도 본인 문서라면 점수·레벨·연속일을 임의로 기록할 수 있다. “타인 문서 쓰기 불가”는 점수 위조 방지가 아니다.
- 완료 기준:
  - 배포 빌드에서 개발자 버튼과 전역 함수가 존재하지 않는다.
  - 수료 조건과 점수를 서버가 원본 제출/시도 데이터로 다시 계산한다.
  - 공식 수료증·리더보드 필드는 클라이언트 직접 쓰기를 차단한다.
  - Firestore Emulator에서 임의 점수/수료증 생성이 거부되는 테스트가 통과한다.
  - 기존 로컬 기록은 `자가 학습 기록`으로 유지하되 `검증된 성취`와 구분한다.

### P1 — 기능 신뢰도와 사용성 문제

#### QA-P1-01 새 핵심 기능이 통합 진도에 연결되지 않음

- `progress-catalog.json`은 368개 항목이다.
- 검색 인덱스는 426개, 최상위 HTML은 428개다.
- `vulnlab.html`, `redteam.html`, `quiz-forge.html`은 통합 진도 카탈로그 ID가 없다.
- 레드팀과 문제 포지는 별도 localStorage 통계를 쓰고, 취약점 실습장은 `wvs_vulnlab`을 쓴다.
- 영향: 사용자는 핵심 기능을 완료해도 `내 기록`에서 하나의 성장 경로로 보지 못한다.
- 제안: 활동 이벤트를 `visited`, `attempted`, `solved`, `verified`로 통합하고 기존 키는 어댑터로 읽는다.

#### QA-P1-02 AI 문제 포지의 “기계 검증됨” 표현이 실제 판정보다 강함

- AI 폴백 규칙 문제는 `verify()` 오류가 있어도 해설에 공백 하나를 추가한 뒤 `기계 검증됨` 배지를 표시한다.
- 폴백 생성은 `검증 통과` 통계에도 반영되지 않아 배지와 통계가 맞지 않는다.
- V2 “답 유일성”은 선택지 문자열 중복과 정답 인덱스만 확인한다. 의미상 정답이 하나인지 검증하지 않는다.
- V3 “근거 충분성”은 해설 길이 40자 이상만 확인한다.
- 제안: 배지를 `스키마 검사 통과`, `규칙 fixture 통과`, `전문가 검토`로 구분한다. 모든 검사 실패 시 출제를 중단하고 실패 조건을 기록한다.

#### QA-P1-03 언어 토글이 AI 상태 배지를 가림

- 위치: `redteam.html`, `quiz-forge.html`
- 고정 `.wvs-langbar`와 우측 `#aiStatus`가 390, 768, 1440px 모두 겹친다.
- 제안: 언어 선택을 공통 헤더 내부에 배치하고 fixed overlay를 제거한다.

#### QA-P1-04 영어 모드가 사실상 부분 번역

- 영어 전환 후 남은 한글 비율: 허브 76.6%, 레드팀 87.3%, 문제 포지 90.0%, 자동차 대표 실습 65.6%, AI 대표 실습 70.8%.
- 전역 사전의 문자열 치환 방식이라 문장이 한글과 영어가 섞이고, 동적으로 생성된 문구는 대부분 번역되지 않는다.
- `vulnlab.html`은 영어 전환 경로가 확인되지 않았다.
- 영향: `html lang="en"`으로 바뀌지만 실제 본문은 한국어라 접근성과 제품 신뢰도가 떨어진다.
- 제안: 대회 제출본이 한국어 중심이면 불완전한 영어 버튼을 숨긴다. 영어를 제공한다면 페이지별 번역 키와 동적 콘텐츠 번역 데이터를 완성한다.

#### QA-P1-05 카탈로그 접기 헤더가 키보드로 접근 불가

- `guide-group` 5개와 다수 `menu-category`가 클릭 가능한 `<div>`다.
- `aria-expanded`는 일반 div에서 지원되지 않고, `tabIndex=-1`이라 Tab으로 도달할 수 없다.
- axe 결과: `aria-allowed-attr` critical 5건.
- 제안: 전부 `<button type="button" aria-expanded aria-controls>`로 변경한다.

#### QA-P1-06 접근성 대비와 폼 레이블

표본 10페이지에서 다음을 재현했다.

- 허브: 색 대비 serious 4건
- 취약점 실습장: 색 대비 serious 8건, 본문 링크 식별 1건
- 자동차/AI 대표 실습: 색 대비 serious 각 10건
- AI 대표 실습: 모델 `<select>` 이름 없음 critical 1건
- SQL 라이브: 입력 5개 레이블 없음 critical 5건
- 공통 `#64748b` 작은 텍스트, 흰색+주황/초록/빨강 배지가 반복적으로 대비 기준에 미달한다.
- 390px에서 `vulnlab.html`의 72개 상호작용 요소 중 69개가 한 변 44px 미만이었다. 실제 WCAG 2.2 최소 24px 또는 충분한 간격 규칙은 요소별 재검사가 필요하다.

제안: 공통 색 토큰을 AA 기준으로 다시 정하고, 보이는 포커스, 레이블, 링크 밑줄, 24px 최소/주요 제어 44px 권장 영역을 자동 회귀 검사에 넣는다.

#### QA-P1-07 전역 검색 대화상자 접근성 및 검색 품질

- dialog에 `aria-modal`이 없고 포커스 트랩과 닫은 뒤 원래 버튼으로 포커스 복귀가 없다.
- 검색 결과 행은 클릭 가능한 div이며 option/link 역할이 없다.
- 인덱스 로딩 중 사용자가 입력하면 로딩 완료 콜백이 빈 검색으로 결과를 덮을 수 있다.
- `자동차` 검색은 0건이고 `CAN` 검색은 3건이다. 자동차 페이지의 키워드에 도메인명·한글 동의어가 없다.
- 제안: WAI-ARIA combobox/listbox 패턴으로 재구성하고 도메인·CWE·한글/영문 동의어·난이도·실습 유형을 검색 필드에 추가한다.

#### QA-P1-08 사용자 API 키를 localStorage에 저장

- 레드팀·AI 튜터는 Anthropic/Z.ai 개인 키를 localStorage에 저장하고 브라우저에서 공급자 API로 직접 보낸다.
- 사이트에는 의도적인 XSS 실습과 많은 인라인 스크립트가 있어, 같은 출처의 DOM 삽입 결함이나 확장 프로그램이 생기면 키 노출 영향이 크다.
- 제안: 대회 공개 모드는 서버 프록시만 사용한다. BYO가 꼭 필요하면 별도 고급 설정, 세션 한정 보관, 명확한 위험 고지, 삭제 확인, CSP 강화가 필요하다.

#### QA-P1-09 AI 프록시 남용·비용 통제

- `/api/ai`는 인증 없이 호출할 수 있고 IP별 일일 12회만 제한한다.
- CORS는 브라우저 출처 제한이며 API 호출 권한 통제가 아니다.
- 공유망 사용자는 한 사람이 한도를 소진하면 함께 차단될 수 있고, 자동화된 직접 요청을 막기 어렵다.
- 제안: 익명 체험도 서버 발급 세션 ID + App Check + 전역 예산 상한 + 요청별 크기/빈도 제한을 적용한다. 로그인 사용자는 uid 기준 한도를 함께 사용한다. 과금이 큰 호출은 제한 사용 토큰 또는 추가 검증을 검토한다.

#### QA-P1-10 PWA 캐시 버전이 고정됨

- `sw.js`의 `VERSION`이 계속 `wvs-v1`이다.
- JS/CSS는 stale-while-revalidate라 기존 사용자가 배포 직후 이전 공통 스크립트를 먼저 받을 수 있다.
- 제안: 배포마다 캐시 버전을 생성하거나 파일명 해시를 사용하고, 새 Service Worker 활성화 후 한 번만 명확한 새로고침 안내를 제공한다.

### P2 — 품질과 유지보수 개선

#### QA-P2-01 루트 홈과 대회 허브가 서로 다른 제품처럼 보임

- `/`의 `index.html`은 보라색 4트랙 학습 포털이다.
- 공통 로고와 `홈` 메뉴는 `vuln-hub.html`로 이동하며, 이 화면은 SOC형 AI 대회 허브다.
- 색, 글꼴, 메시지, 메뉴 구조가 달라 사용자는 홈이 두 개라고 느낄 수 있다.
- 제안: `/`을 대회용 통합 홈으로 만들고 기존 4트랙은 `분야별 학습` 섹션으로 흡수한다.

#### QA-P2-02 숫자와 제품 설명이 분산됨

- 홈: 319개+ 실습
- 허브: 425 학습 페이지
- 검색 인덱스: 426 페이지
- 실제 최상위 HTML: 428개
- 진도 카탈로그: 368개
- 시나리오 DB: 230개
- 취약점 실습장: 51미션

각 숫자의 정의가 다를 수 있지만 UI에서 설명되지 않는다. 하나의 빌드 메타 파일에서 자동 집계하고 `학습 페이지`, `시나리오`, `검증형 미션`을 구분한다.

#### QA-P2-03 문서 구조

- 428개 중 `<main>`이 없는 페이지가 421개다.
- H1이 없는 페이지 4개: `classroom.html`, `exam-runner.html`, `quiz-forge.html`, `redteam.html`.
- H1이 2개 이상인 페이지 3개: `03_code_xss.html`, `sim-dast.html`, `sim-source-comments.html`.
- `sim-test.html`에는 `<html lang>`이 없다.

생성 템플릿에서 skip link, header/nav/main/footer, H1 한 개, 문서 언어를 강제한다.

#### QA-P2-04 생성기와 결과물 동기화

이번 SRI 문제는 결과 HTML만 고치면 생성기를 다시 실행할 때 재발할 수 있었다. 변경은 생성기와 생성물 모두 검사해야 한다. 생성 결과를 Git에서 직접 수백 개 수정하는 방식 대신 대표 템플릿 스냅샷과 생성 후 검사를 둔다.

## 5. UI 재설계 우선안

### 5.1 첫 화면

현재 카드 4개보다 다음 3개 행동을 먼저 제시한다.

1. `3분 진단하고 추천받기`
2. `대표 사건 바로 시작`
3. `이어서 학습`

아래에 웹·인프라·금융·OT·AI·자동차 분야를 배치한다. 대회 메시지인 “AI가 공격하고, 내가 방어하고, 시스템이 검증한다”는 첫 화면 한 문장으로 고정한다.

### 5.2 모바일 내비게이션

- 상단: 로고, 검색, 더보기
- 하단: 홈, 실습, 사건, 내 성장
- 긴 가로 메뉴와 숨겨진 스크롤 메뉴를 제거한다.
- 페이지별 중복 내비게이션은 공통 셸로 통합한다.

### 5.3 실습 화면

- 상단에 `목표 → 관찰 → 공격/진단 → 수정 → 재검증 → 설명` 진행 단계를 표시한다.
- 패치 전/후 결과를 나란히 비교하고 어떤 조건이 통과했는지 보여준다.
- AI 코치는 별도 페이지보다 현재 로그, 선택, 실패 조건을 읽는 우측 패널/모바일 탭으로 제공한다.
- 해설은 정답만 말하지 않고 `증거`, `원인`, `수정`, `재검증` 네 칸으로 고정한다.

### 5.4 성장 화면

`페이지 방문`, `연습 완료`, `서버 검증 통과`, `새 분야 전이 문제 통과`를 분리한다. XP는 동기부여 수치로 표시하고 검증 점수와 섞지 않는다.

## 6. 기능 개선 제안

### 6.1 가장 추천: 통합 사고대응 캠페인

현재 자산을 한 사건으로 연결한다.

```text
레드팀이 공격 경로 선택
  → 취약점 실습장에서 재현
  → 코드/설정 패치
  → 동일 입력으로 재검증
  → AI가 증거 기반 보고서 피드백
  → 내 성장에 검증 결과 저장
```

첫 캠페인은 `웹 API 권한 오류 → OT 원격접속 → 차량 OTA → 개인정보 유출`로 구성한다. 새 페이지를 많이 만들기보다 기존 실습을 표준 이벤트로 연결한다.

### 6.2 증거 기반 AI 코치

AI 입력을 전체 대화가 아니라 현재 lab ID, 단계, 최근 요청/응답, 실패한 검증 조건, 사용한 힌트로 제한한다. AI 응답에는 내부 콘텐츠 source ID를 포함하고 서버가 실제 존재하는 출처인지 확인한다.

### 6.3 오개념 진단

오답을 단순 저장하지 말고 `인증과 인가 혼동`, `암호화로 접근통제까지 해결된다고 생각함`, `탐지와 예방 혼동` 같은 원인 태그로 모은다. 다음 추천은 이 태그와 선수학습으로 설명한다.

### 6.4 콘텐츠 신뢰도 표시

각 실습에 다음을 노출한다.

- 실습 유형: 개념 시뮬레이션 / 브라우저 실행 / 서버 검증
- 출처와 버전
- 마지막 전문가 검토일
- 적용 범위와 한계

`ISO/SAE 21434 기반`, `KISA 전수` 같은 문구는 실제 항목 매핑과 검토 근거가 있는 범위만 사용한다.

### 6.5 강사용 증거 리포트

기존 강의실 기능에 단순 완료율 대신 `어떤 증거를 보고 어떤 수정으로 재검증했는지`를 추가한다. 학생 개인정보와 자유 대화 원문은 기본 수집하지 않는다.
