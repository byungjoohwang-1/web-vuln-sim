## 1. 해결 문제

> **다 막으면 서비스가 죽고, 다 열면 사고가 턴다 — 그 선을 직접 긋게 만드는 보안 실습장.**

가이드를 읽고 퀴즈까지 맞힌 학습자도, 실제 요청·로그·설정 파일 앞에서는 무엇이 잘못됐는지, 고치면 서비스가 죽지는 않을지 판단이 서지 않는다. 가이드는 무엇이 위험한지는 알려주지만, 내 상황에서 무엇을 어떻게 고칠지는 가르쳐주지 않기 때문이다.

**WEB-VULN-SIM**(https://vuln-sim.web.app)은 이 간극을 브라우저 안에서 닫는 한국어 보안 실무 교육 포털이다. 차량 데이터 접근 사고 같은 합성 사건에서 학습자가 직접 방어 정책을 짜고 시험하게 하고, 고정 검사기가 "비인가 차단"과 "정상 동작 유지"를 함께 판정해 전부 거부하는 꼼수가 만점이 되지 않게 한다. 실패한 검사가 남긴 증거는 AI 코치가 읽어 다음 수정 행동을 제안하고, 고친 결과는 다시 같은 검사기로 확인된다. 이렇게 배운 방어 원리는 금융·자동차 등 다른 산업의 과제로 이어져 다시 시험되며, 500여 종의 학습 항목이 같은 흐름 아래 하나의 한국어 포털로 연결된다.

## 2. AI 활용 방식

WEB-VULN-SIM(https://vuln-sim.web.app)은 한국어 보안 실무 교육 포털입니다. AI는 이 사이트에서 "정답을 알려주는 존재"가 아니라, 고정 검사기에 막힌 학습자에게 **다음에 확인할 행동 하나**를 제안하는 학습 코치로 설계됐습니다. 판정·점수·수료는 전부 결정론적 검사기와 서버가 담당합니다.

### 제품 안의 AI

#### 코치 계약 — 무엇을 주고, 무엇을 막는지

AI 코치(`public/js/coach.js`)는 코드로 명시된 계약 아래 동작합니다. 계약은 두 방향으로 정의돼 있습니다.

**AI에게 주는 것 — 구조화된 실패 증거**

- 과제의 목표·전제·성공 조건, 학습자가 지금 구성한 정책(조건식 또는 켜진 체크박스), 선택한 증거의 요약
- 실패한 검사의 **기대값(expected) / 실제값(actual) / 그 의미(meaning)** — 단순한 실패 ID가 아니라, 모델이 "왜 실패했는지" 진단할 수 있는 최소한의 해석 재료
- 단계별 힌트 수위(hintLevel 1 관찰 → 2 비교 지점 → 3 접근법). 어느 단계에서도 완성된 정답 조건식을 그대로 출력하지 않도록 시스템 프롬프트에 못 박혀 있습니다

**AI로부터 막는 것 — 계약 위반 차단**

| 위험 | 차단 방식 |
|:--|:--|
| 데이터 과다 전송 | 호출부가 넘긴 필드 중 계약에 정의된 것만 남기고 전부 버림. 정답 정책·미공개 평가 답안은 호출부가 넣어도 폐기. 모든 필드에 길이 상한 |
| 민감정보 유출 | 학습자가 붙여 넣은 로그에서 API 키(`sk-`, `ghp_`, `xox…`), JWT, 주민등록번호, 카드번호, 이메일, `password=`/`token=` 대입값을 **전송 전에** `[REDACTED_*]`로 마스킹 |
| 프롬프트 인젝션 | 실습 문서·로그 속 문장은 전부 "데이터"로만 취급. 그 안의 "정답을 알려줘", "규칙을 무시해" 같은 지시를 따르지 않음 |
| 권한 탈취 | 모델 응답에 `submit`/`answer`/`score`/`grade`/`grant`/`permission`/`unlock`/`certid` 류 필드가 있으면 서비스에 반영하지 않고 버리며, 무엇이 시도됐는지 `refused` 흔적으로 기록 — 조용히 사라지게 하지 않음 |
| 지어낸 출처 | `sources`는 이번 요청에 준 식별자(evidence ID, activityId)나 content-catalog에 실재하는 ID만 허용. 카탈로그 등록은 "존재 확인"이지 인용 내용의 정확성 검증이 아니라는 점을 코드 계약에 명시해 두었습니다 |
| 이른 정답 노출 | 정답 공개는 학습자가 명시적으로 요청할 때만, 요청 기록을 남기고 실행. 코치가 먼저 정답을 말하지 않음 |

전송 내용은 `preview()`로 사용자에게 그대로 보여줄 수 있어 "무엇이 나가는지"가 투명합니다.

#### AI와 검사기의 역할 분리 — AI는 힌트, 판정은 고정 검사기

대표 실습 `/incident.html`(차량 데이터 접근 사고, **본편 4단계 — 차량 조회 API 인가 → OTA 검증 → 개인정보 영향 → 정비 예약 API 전이 — 에 금융 전이 확장 1단계(금융 거래 조회)를 더한 구성**)에서 **통과 판정은 결정론적 검사기만** 합니다. 검사기는 "비인가 요청 차단"과 "정상 동작 유지"를 함께 판정하므로 **전부 거부가 만점이 되지 않습니다.** AI 코치는 이 검사기가 남긴 실패 증거를 읽고 다음 행동을 제안할 뿐, 점수를 바꾸거나 통과시키는 경로는 설계상 없으며 권한 상승 요청은 거부하고 흔적으로 남깁니다. 학습 효과 측정이 아니라 "막힌 지점을 스스로 넘게 돕는다"가 코치의 목적이고, 시스템 프롬프트도 "전부 거부 류의 해결책을 권하지 않는다"는 조항을 포함합니다.

#### 3계층 클라이언트 — 키 없는 방문자도 실제 AI를 체험

`public/js/ai-client.js`는 세 계층으로 내려가는 클라이언트입니다.

1. **BYO(자기 키)** — 사용자 개인 API 키로 브라우저에서 Anthropic 또는 Z.ai(GLM) API에 직접 호출. 키는 기본 **sessionStorage**(탭 종료 시 소멸)에 보관합니다. XSS 시뮬레이터를 직접 호스팅하는 사이트 특성상 localStorage 노출 창을 탭 수명으로 줄이기 위한 선택이며, 영구 저장은 사용자가 명시적으로 고릅니다.
2. **공유 프록시 `/api/ai`** — 키가 없는 일반 방문자도 실제 모델(claude-haiku-4-5) 응답을 받습니다. IP당 일일 횟수 제한(하루 40회)과 전체 일일 예산 상한(1,500회)으로 비용을 유한하게 묶어 둡니다.
3. **규칙 기반 폴백** — 두 계층 모두 실패하면 실패한 검사의 기대값/실제값 구조만으로 안내 문장을 조립합니다. 이때 반드시 "기본 도움말이며 모델이 증거를 읽고 판단한 것이 아니다"고 표시해 규칙 응답을 AI 응답으로 속이지 않습니다. 코치 호출은 예외를 던지지 않으므로 **AI가 죽어도 실습은 계속됩니다.**

### AI 효과의 평가

AI 코치의 효과는 `/coach-eval.html`에 **"측정한 것"과 "측정하지 않은 것"을 나눠** 공개합니다. 돌리지 않은 평가는 수치를 지어내지 않고 "미측정" 태그로 남기는 것이 이 페이지의 원칙입니다.

- **오프라인 계약 평가(측정함)** — 고정 픽스처 35개로 파이프라인이 계약을 지키는지(마스킹 적용, 지어낸 출처 제거, 금지 필드 거부, 폴백 동작)를 자동 검증하며 전부 통과했습니다. 단 이것이 보장하는 것은 "계약 위반 차단"이지, 모델 답변의 교육적 정확성이 아니라고 페이지에 명시돼 있습니다.
- **실제 모델 평가(2026-09-17 실행)** — 실측 대상 픽스처 28개를 일반 AI 조건(계약 없이 학습자가 챗봇에 쓸 법한 질문만 준 상태)과 구조화 코치 조건(운용 경로 그대로)의 2조건으로 실행했습니다(총 56호출). 평가기는 서비스와 같은 시스템 프롬프트·같은 입력 조립 경로를 그대로 써서, **평가하는 프롬프트와 서비스하는 프롬프트가 어긋나지 않게** 했습니다. 응답 품질 판정은 정규식 자동 채점을 하지 않고 사람/에이전트 검토 단계에서 하며, 원시 응답은 jsonl로 보존합니다. 결과 수치는 **리포트 페이지(/coach-eval.html)를 참조**해 주세요.
- **명시적 한계** — 사용자 관찰·학습 효과 실험은 아직 수행하지 않았습니다. 계약 평가 통과가 곧 학습 효과를 의미하지 않는다는 한계를 그대로 적어 두었습니다.

실측이 실제 코드를 개선한 사례도 있습니다. 실측 평가에서 모델이 과잉 괄호를 붙이는 응답이 관측되었고, 기존 JSON 추출기가 이를 파싱하지 못해 좋은 응답이 폴백으로 떨어지던 결함을 발견해 괄호 깊이를 세는 파서로 교체했습니다.

### 개발 과정의 AI

개발에는 Claude Code(모델 GLM)를 사용했으며, 이 저장소의 원칙은 **"AI가 생성했으면 반드시 기계가 검증하고, 사람이 검토 없이는 발행하지 않는다"**입니다.

- **생성기 파이프라인(`_gen/`)** — 595페이지 학습 콘텐츠를 손으로 편집하지 않고 Python 생성기로 일관되게 생성·주입합니다(공통 셸·접근성 주입, 콘텐츠 레지스트리, 안전 고지, sitemap, 진도 엔진, 서버·보안장비 진단 랩 등). 스킵링크·랜드마크·진도·이전-다음 같은 전 페이지 일관성은 사람이 아니라 생성기와 검증기가 보장합니다.
- **검증 게이트** — 배포 전 `validate_build.py`(레지스트리-화면 수치 일치, 주입 산출물 문법, PDF 합자 깨짐 등)와 stamp-build/predeploy 배포 게이트를 통과해야 합니다. QA 정적 검사기 17종을 3회 반복 실행(`qa-suite.js`)해 일시적 오탐과 진짜 결함을 분리합니다. **AI가 만든 결과물도 동일한 게이트를 통과해야 하며, 정적 콘텐츠(호스팅)는 이 게이트를 통과해야만 배포됩니다.**
- **"검토 없는 발행 금지" 이 원칙의 유래** — 과거 주입 스크립트가 문서가 아니라 JS 문자열 내부의 첫 `</body>`를 치환해 페이지 6개가 죽은 실제 사고에서 나온 원칙입니다. 이후 문서 끝 탐색 규칙(`rfind`)과 검증 항목이 코드와 문서 모두에 못 박혔고, 그 검증기 자체도 AI가 작성하고 사람이 검토했습니다. AI가 만든 검사기와 테스트가 AI가 만든 콘텐츠를 서로 묶는 구조로 운영합니다.
- **신뢰 경계의 일관성** — 수료 판정·발급은 Cloud Functions 서버가 채점하고 HMAC으로 서명하며, 클라이언트 직접 쓰기는 Firestore 규칙으로 차단합니다(에뮬레이터 규칙 테스트 15개). 브라우저와 AI 어느 쪽도 신뢰 경계 안에 들어가지 않습니다.

요약하면, 이 프로젝트에서 AI는 (1) 제품 안에서는 계약으로 묶인 힌트 코치, (2) 평가에서는 측정/미측정을 분리해 공개하는 대상, (3) 개발에서는 검증 게이트를 통과해야만 발행되는 생성 도구로 — 세 위치 모두에서 **결정 권한은 사람과 고정 검사기에 둔 채** 활용되고 있습니다.

> **출처·제휴 관계**: 이 포털의 학습 콘텐츠는 KISA·금융보안원·개인정보보호위원회의 공개 가이드를 개념적으로 재구성한 것이며, 해당 기관의 공식 서비스가 아니고 어떠한 제휴·승인 관계도 아닙니다.

### 제품 스택

**호스팅·백엔드 — Firebase**

| 구성 요소 | 역할 |
|:--|:--|
| Firebase Hosting | 라이브 서비스(https://vuln-sim.web.app). 정적 HTML 595페이지 배포, 보안 헤더·CSP·캐시 정책·301 리다이렉트를 `firebase.json`에서 선언적으로 관리 |
| Cloud Functions (Node.js) | 서버 신뢰 경계. `/api/ai`(AI 프록시), `/certApi`(시험 문항 배부→서버 채점→HMAC 서명 수료증 발급·검증), `/accountApi`(계정 데이터 내보내기·삭제) |
| Firestore | 로그인 사용자의 학습 진도 동기화. 규칙 기본값은 거부이며, 수료증 문서의 클라이언트 직접 쓰기는 차단(에뮬레이터 규칙 테스트 15개로 확인) |

**프론트엔드 — 프레임워크 없는 순수 정적 HTML+CSS+JS**

React/Vue 같은 프레임워크와 번들러 없이, 브라우저에서 바로 도는 바닐라 JS만 사용합니다. 학습 카탈로그 518항목("500여 종" 표기) 전부가 같은 구조의 정적 페이지이고, 서비스 워커(`sw.js`)로 오프라인 PWA까지 동작합니다.

**콘텐츠 파이프라인 — Python 생성기(`_gen/` 약 200개 스크립트)**

595페이지를 손으로 쓰고 유지할 수는 없으므로, 콘텐츠를 "코드"로 다루는 파이프라인을 구축했습니다.

- `specs_*.py` — 각 학습 기둥의 콘텐츠를 데이터(스펙)로 정의
- `gen_*.py` / `inject_*.py` — 스펙에서 HTML을 생성하고, 공통 셸·진도 엔진·안전 고지를 멱등적으로 주입
- `validate_build.py` — 생성물 검증: 스크립트 블록 문법, 내부 링크, SRI 해시, 백도어 함수 존재 여부, 화면 수치와 레지스트리 일치 등 13종 이상의 정적 검사
- 배포 게이트 3중: `stamp-build.js`(빌드 스탬프·수치 드리프트) → `predeploy-check.js`(검사기 묶음, hosting 배포 시 firebase 도구가 자동으로 실행) → `python _gen/validate_build.py`

**QA — 정적 검사기 17종 × 3회 반복(`tools/qa-suite.js`)**

한 번의 실행 결과는 일시적 오탐일 수 있으므로, 전 검사기를 3회 연속 돌려 "매번 실패하는 진짜 결함"과 "간헐적으로 걸리는 오탐"을 분리합니다.

### AI 도구와 모델

**1. 개발 과정의 AI — Claude Code (GLM 계열 모델)**

저장소의 생성기 파이프라인(`_gen/`)과 검증 게이트 대부분을 Claude Code로 구축·유지했습니다. 단, "사람이 검토하지 않은 생성물은 발행하지 않는다"가 원칙이며, 이 원칙 자체를 배포 게이트(기계 검증)로 강제했습니다. 실제로 게이트가 잡아낸 결함(생성기가 JS 문자열 안의 `</body>`를 치환해 페이지 6개가 죽은 사고 등)이 CLAUDE.md에 기록되어 재발 방지 검사로 남아 있습니다.

**2. 제품 안의 AI — 3계층 클라이언트 + 서버 프록시**

제품 AI(실습 코치, 대표 체험 `/incident.html`의 코치)는 단일 진입점이 아니라 폴백 사슬입니다.

```
사용자 BYO 키(직접 입력) → 공유 프록시 /api/ai → 페이지 내 규칙 기반 데모 엔진
```

- **BYO 키**: 사용자 자신의 Anthropic / Z.ai GLM 키. 기본은 탭을 닫으면 사라지는 sessionStorage 보관(XSS 시뮬레이터를 직접 호스팅하는 사이트 특성상 같은 출처 스크립트가 localStorage를 읽을 수 있기 때문)
- **공유 프록시**(Cloud Functions): 팀 공유 키는 브라우저가 아니라 서버만 읽을 수 있는 Firestore 구성 문서에 두고 브라우저에 노출하지 않습니다. 프로바이더는 키 형식으로 자동 판별 — Anthropic(claude-haiku-4-5, claude-sonnet-4-6) / Z.ai GLM(glm-4.6, glm-4.5 등). IP당 일일 40회 + 사이트 전체 일일 상한 1,500회, 메시지 14개·문장 4,000자·max_tokens 800 상한으로 비용을 유한하게 묶었습니다
- **규칙 기반 폴백**: 키가 없어도 데모가 동작하며, 화면에는 "기본 도움말"로 명시해 AI 응답인 것처럼 속이지 않습니다

**3. 채점은 AI가 하지 않는다 — 고정 검사기 + 서버**

AI 코치에는 계약을 걸었습니다: 최소 데이터만 전송, 민감정보 마스킹, 정답·점수는 아예 분리해서 보내지 않음, 출처는 제공된 식별자만 인용, 권한 상승 요청은 거부하고 기록. 실습 판정은 전부 결정론적 검사기가 하고(예: 차량 사고 시나리오에서 "정상 동작 유지 + 비인가 차단"을 함께 판정해 전부 거부가 만점이 되지 않게 함), 수료 판정은 Cloud Functions가 채점하고 HMAC으로 서명합니다.

**4. AI 품질 측정 — `/coach-eval.html`**

오프라인 계약 평가 픽스처 35개를 전부 통과했고, 실제 모델을 대상으로 한 평가(일반 AI/구조화 코치 2조건, 28픽스처×2=56호출)를 2026-09-17에 실행했습니다. 결과 수치는 리포트 페이지(/coach-eval.html)를 참조하세요. "측정한 것"과 "측정하지 않은 것"(사용자 학습 효과 — 아직 실험하지 않음)을 분리해 적습니다.

### 그 이유

**왜 프레임워크 없는 정적 파이프라인인가 — 검증 가능성**

보안 교육 포털이 스스로 결함을 내면 신뢰가 무너집니다. 프레임워크와 빌드 체인이 없으면 "배포되는 것 = 저장소에 있는 것 그대로"가 되어, 정적 검사기가 전체를 대상으로 검증할 수 있습니다. 595페이지에서 수치 하나를 고치면 여러 화면 표기가 어긋나던 문제도, 수치의 단일 원천(`content-registry.json`)과 대비값 일치 검사로 잡아냈습니다. AI(생성 도구)의 산출물은 필연적으로 흠결을 포함하므로, 저희는 AI를 믿는 대신 **AI가 만든 것을 기계가 검증하는 구조**에 투자했습니다. 생성기가 잘못 만들면 배포 게이트가 차단합니다.

**왜 서버 채점인가 — 신뢰 경계**

학습자가 콘솔을 열면 클라이언트의 모든 판정은 우회 가능합니다. 실제로 개발 중 `forceUnlockForDev()`라는 디버그 함수 한 줄로 수료증이 발급되던 적이 있었고, 이를 계기로 수료 판정·발급·서명 전부를 Cloud Functions로 옮기고 클라이언트 직접 쓰기를 Firestore 규칙으로 차단했습니다(에뮬레이터 테스트 15개로 확인). "AI가 채점한다"가 아니라 "AI는 코칭만 하고, 판정은 결정론적 검사기와 서버가 한다"는 것이 이 제품의 신뢰 설계입니다.

**왜 AI를 3계층으로 나누는가 — 접근성과 비용의 균형**

키 없는 방문자에게 맞는 규칙 기반 데모, 가벼운 체험자에게 맞는 제한된 공유 프록시, 깊이 쓰는 사용자의 BYO 키. 어느 계층에서든 화면이 죽거나 비용이 무한정 늘지 않도록 상한을 서버에 두었습니다.

> **출처·제휴 관계**: 이 포털의 학습 콘텐츠는 KISA·금융보안원·개인정보보호위원회의 공개 가이드를 개념적으로 재구성한 것이며, 해당 기관의 공식 서비스가 아니고 어떠한 제휴·승인 관계도 아닙니다.
